# Agent Readiness Plan — playground marketplace

_Generated by `/agent-readiness` on 2026-09-04. This is a **plan**, not documentation.
It is an ordered list of interventions; a separate session (or you) carries them out._

> **Status (2026-09-04):** Items 1, 2, 3, 4, and 6 have been implemented. Item 5
> (plugin-authoring / CONTRIBUTING manual) is **deliberately deferred** by the author
> until there is contributor interest.

## Context established this session

- **What the repo is:** a Claude Code **plugin marketplace** — a catalog of 5 installable
  plugins under `plugins/`, indexed by `.claude-plugin/marketplace.json`. The product is
  almost entirely Markdown (SKILL.md, agent definitions, reference catalogs); `redteam`
  also carries real shell (`scripts/`, `hooks/`, `scripts/tests/`).
- **Design axiom (confirmed by the author, uninferable from the code):** every plugin is a
  **self-contained adaptation of a workflow into the Claude / Claude Code ecosystem that
  assumes no external connectivity.** It is a complementary base layer; adopters bridge it
  to their own systems by layering in their **own connectors / MCPs** (e.g. Drata/Vanta for
  vendor-review, Google Drive for the tabletops). Connector-agnostic, adopt-and-extend, is
  the through-line for the *whole* marketplace, not just vendor-review.
- **`docs/agents/` is the author's personal project-management layer** (issue tracking,
  triage labels, domain-modeling) driven by [Matt Pocock's skills](https://github.com/mattpocock/skills).
  It is load-bearing *for the author*, correctly references an external skill set that is
  intentionally not vendored here, and is deliberately **not** the plugins' own logic.
  The `mattpocock/skills` label reference and the `/wayfinder`, `/triage` command
  references are accurate for that workflow — **not** stale drift. Leave them alone.
- **Primary next reader (stated priority):** **adopters** — people who discover the
  marketplace, install a plugin (especially `agent-readiness`), and run it against their
  own project. The ranking below puts the adopter's journey ahead of author/contributor
  concerns.
- **Baseline floor is largely met as files:** `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`,
  root `README.md`, and per-plugin READMEs all exist. The gaps below are **content** gaps,
  not missing-file gaps — except where noted.

## Interventions (ranked — adopter journey first)

### 1. Raise the design axiom to a marketplace-level principle in the root README
**Outcome:** The root `README.md` states the mental model that makes every plugin make
sense — self-contained, assumes no external connectivity, adopt-and-extend by layering in
your own connectors/MCPs — as a first-class section, not one passing sentence.
**Why it matters:** This is the single most load-bearing, most uninferable fact about the
repo, and the thing your priority reader (the adopter) most needs to *get* before they
install anything. Right now it lives fully only in `vendor-review`'s README and in a
single, typo'd sentence of the root README (`"For examply..."`, README.md:6). An adopter
reading the front door doesn't learn the model.
**What it unblocks:** Every downstream adopter decision ("why doesn't this just call my
system?", "how do I connect it to mine?") and every plugin README's consistency.
**Also fold in:** fix the `For examply` typo; the section can point at #4 (extension guide)
once that exists.
**Skill:** `/writing-for-agents` (present in this environment) for the doc conventions.

### 2. Give `agent-readiness` (the priority plugin) an install/run block in its own README
**Outcome:** `plugins/agent-readiness/README.md` carries the same
`## Claude Code usage` install + run block that `vendor-review`'s README already has
(`/plugin marketplace add …`, `/plugin install agent-readiness@playground`, then
`/agent-readiness:agent-readiness`).
**Why it matters:** This is the plugin you most want people to grab and run on their own
projects — and its README is the one adopter-facing README with **no install or run
instructions** (agent-readiness/README.md, 45 lines; compare vendor-review/README.md:22-34).
**What it unblocks:** The exact adopter journey you named: discover → install → run against
their project.
**Skill:** none needed — a small, mechanical README edit; `/writing-for-agents` optional.

### 3. Record the design axiom as an ADR (a stated, durable decision)
**Outcome:** A short ADR — e.g. `docs/adr/0001-connectivity-free-adopt-and-extend.md` —
capturing the decision that plugins assume no external connectivity and are extended by the
adopter's own connectors/MCPs, with the rationale (portability, no bundled credentials,
Claude/Claude Code as the ecosystem boundary).
**Why it matters:** Right now the axiom is enforced only by the author's memory and is
carried *inconsistently* across plugin READMEs (vendor-review states it explicitly; others
imply it or omit it). An ADR makes it the reference every plugin README and every future
plugin can point back to, so it can't silently drift.
**What it unblocks:** Consistency across all current and future plugin READMEs; a check any
agent or contributor can apply to a new plugin ("does this respect the no-connectivity
axiom?"). Also **resolves a latent inconsistency**: `CONTEXT.md` and `docs/agents/domain.md`
both reference `docs/adr/`, which does not yet exist — this creates the directory their own
convention already assumes.
**Skill:** `/domain-modeling` (present) — it owns ADR creation in this environment.

### 4. Write an extension guide — "layer your own connectors/MCPs onto a plugin"
**Outcome:** A doc (e.g. `docs/extending-plugins.md`, linked from the root README) that
shows, concretely, how an adopter bridges a base plugin to their own stack: the worked
`vendor-review` + Drata/Vanta example, the tabletop + Google Drive example, and the general
pattern (install the plugin, add your MCP/connector, let the plugin propose actions the
connector fulfills).
**Why it matters:** The adopt-and-extend model is the *value proposition*, but today an
adopter is told it's possible (vendor-review README names Drata/Vanta) without being shown
*how*. This converts the vision into something an adopter can act on.
**What it unblocks:** Adopters going beyond the self-contained base — the second half of the
journey, and the thing that turns a trial into real integration.
**Skill:** `/writing-for-agents` (present) for structure/conventions.

### 5. Write a plugin-authoring / CONTRIBUTING manual ("how to add plugin #6")
**Outcome:** A `CONTRIBUTING.md` (or `docs/authoring-a-plugin.md`) covering the required
structure (`.claude-plugin/plugin.json`, `skills/`, `agents/`, `commands/`, `hooks/`,
`references/`), the repeated `references/`-split pattern seen across plugins, versioning
(the per-plugin `version` field), how to register a plugin (edit `marketplace.json` **and**
the root README table), and how to validate it before shipping (e.g. `claude plugin eval`;
`redteam` also has `scripts/tests/` as a live example).
**Why it matters:** This is the *actual work* done in this repo, and it is entirely
undocumented — `AGENTS.md` describes your management workflow but nothing about authoring.
An agent asked to "add a plugin" or "fix the redteam scope guard" has no operating manual.
Ranked below the adopter items per your stated priority, but it's the top author/contributor
gap.
**What it unblocks:** You-plus-an-agent building and maintaining plugins; outside
contributors adding plugin #6 without reverse-engineering the conventions.
**Follow-on:** once it exists, add a one-line pointer to it from `AGENTS.md` so the agent
front door reaches it.
**Skill:** no installed skill specifically writes a CONTRIBUTING/authoring guide;
`/writing-for-agents` (present) is the closest fit for the conventions.

### 6. Extend `CONTEXT.md` to cover intra-plugin vocabulary
**Outcome:** Add glossary entries for the vocabulary *inside* a plugin — Skill vs Agent vs
Command vs Reference catalog, the `references/` pattern, and cross-plugin domain terms like
`target-kind` (redteam) and `maturity tier` (tabletops).
**Why it matters:** `CONTEXT.md` is a strong glossary, but it stops at the marketplace level
(Marketplace, Plugin, Category, Policy). An agent working *inside* a plugin has no shared
language for the parts it's editing.
**What it unblocks:** Cheaper, less ambiguous reads for any agent editing plugin internals;
supports interventions #4 and #5.
**Skill:** `/domain-modeling` (present) — it owns `CONTEXT.md` in this environment.

## Deliberately NOT recommended

- **Removing or "fixing" `docs/agents/` references to `mattpocock/skills`, `/wayfinder`,
  `/triage`, etc.** — confirmed accurate for the author's personal management workflow, not
  drift.
- **Documenting each plugin's internal logic here** — out of scope for this front-door plan;
  the per-plugin READMEs and SKILL.md files already carry that, and this session plans docs,
  it doesn't write them.

## Suggested execution order

1 → 2 → 3 → 4 (adopter journey, front to back), then 5 → 6 (author/contributor depth).
Items 1 and 2 are quick and high-leverage; do them first.
